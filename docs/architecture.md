# Architecture Overview

## Project Goal

This project implements a simple task dashboard for a work manager.

The system loads thousands of tasks from a local data source, filters active tasks, displays them in a browser, and presents timing measurements from both the backend and frontend.

The assignment requirements are covered by:

- A data source containing at least 5,000 generated tasks
- A backend API that returns only `Pending` and `InProgress` tasks
- A frontend page that displays the returned tasks
- Backend timing measurement
- Frontend API roundtrip timing measurement
- Frontend render timing measurement
- Total count display
- A seed script for generating test data

## Technology Choices

### Backend

The backend is implemented with Python and FastAPI.

The assignment allowed either .NET Core or Python. I chose Python in order to focus on a clean implementation, clear API behavior, and reliable timing measurements.

FastAPI was selected because it provides:

- A simple and readable API structure
- Built-in JSON response handling
- Easy local development with Uvicorn
- Low overhead for a focused backend service

### Database

SQLite is used as the local data source.

SQLite was chosen because it is:

- Lightweight
- Easy to run locally
- Suitable for a small standalone assignment
- Simple to inspect using database tools
- Suitable for storing and querying thousands of generated tasks in a local assignment environment

The database is generated by `backend/seed_data.py`.

The database file itself is not committed to Git. It can be recreated by running the seed script.

### Frontend

The frontend is implemented with plain HTML, CSS, and JavaScript.

No frontend framework was used because the assignment requires a simple page. Avoiding unnecessary framework setup keeps the solution easier to review, run, and understand.

## Data Model

Each task contains:

| Field | Description |
|---|---|
| `TaskID` | Numeric task identifier |
| `Title` | Task title |
| `Status` | One of `Pending`, `InProgress`, `Completed` |
| `Priority` | One of `Low`, `Medium`, `High` |

The backend filters out completed tasks and returns only:

- `Pending`
- `InProgress`

This matches the assignment requirement to skip completed tasks.

## System Flow

```text
Browser
  |
  | GET /api/tasks
  v
FastAPI Backend
  |
  | SELECT TaskID, Title, Status, Priority
  | FROM tasks
  | WHERE Status IN ('Pending', 'InProgress')
  v
SQLite Database
  |
  v
JSON Response
  |
  v
Frontend Table + Timing Metrics
```

## API Design

### GET `/health`

Simple health check endpoint.

Example response:

```json
{
  "status": "ok"
}
```

### GET `/api/tasks`

Returns all active tasks whose status is either `Pending` or `InProgress`.

Example response:

```json
{
  "tasks": [
    {
      "taskId": 1,
      "title": "Generated task #1",
      "status": "Pending",
      "priority": "High"
    }
  ],
  "total": 3334,
  "backendDurationMs": 8.42
}
```

## Timing Measurements

The system includes three timing measurements.

### Backend Duration

Measured in the backend using Python's `perf_counter`.

This measures the time required to:

- Query the SQLite database
- Convert rows into response objects
- Prepare the response payload

The measured value is returned as:

```json
"backendDurationMs": 8.42
```

### API Roundtrip Duration

Measured in the browser using `performance.now()`.

This measures the time from just before the frontend sends the API request until the JSON response is available in the browser.

### Browser Render Duration

Measured in the browser using `performance.now()`.

This measures the time required to render the task rows into the HTML table.

## Rendering Modes

The frontend includes two rendering modes.

### Full Render

This is the default mode.

It renders all tasks returned by the backend. This mode was kept intentionally because the assignment asks to display the task list and measure how long the browser takes to render the rows.

### Paginated Mode

This is an optional performance-oriented improvement.

It displays 100 tasks per page while keeping the full dataset available in the frontend. This demonstrates how the UI can reduce DOM load when working with thousands of rows.

The API behavior does not change between modes. It still returns all active tasks. Pagination is implemented only as a frontend rendering optimization.

## Design Notes

The solution intentionally avoids unnecessary complexity.

Not included:

- Authentication
- User management
- Server-side pagination
- Docker
- Heavy ORM usage
- Frontend framework setup

This keeps the implementation focused on the assignment requirements while still showing one practical frontend performance improvement through the optional paginated rendering mode.
